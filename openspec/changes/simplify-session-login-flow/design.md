## Context

当前 demo 的客户端登录窗口仍以“账号输入”组织交互，而服务端登录协议 `PlayerLoginMsg_s` 也要求客户端上传 `playerID`。这和项目当前目标不一致：该 demo 只需要完成连接、匹配、进入帧同步世界和执行预测回滚，不需要真实账号、密码、注册或用户资料持久化。

现有服务端已经把后续匹配和对局逻辑建立在 `session.player` 上，说明真正需要的是“为当前连接建立玩家上下文”，而不是“让客户端声明自己是谁”。因此这个变更是一次跨 client/server/protocol 的简化性重构，需要先明确协议边界，再进入实现。

## Goals / Non-Goals

**Goals:**
- 将 demo 登录流收敛为纯 session 的匿名入场流程
- 由服务端为当前 session 创建临时 `Player`
- 客户端点击 `LoginWindow` 后只触发入场，不再提交自定义 `playerID` 作为权威身份
- 让匹配、进房、帧同步消息都依赖已绑定的服务端玩家上下文
- 保持改动尽量小，优先复用现有 `LoginService`、`MatchService` 和 `session.player` 结构

**Non-Goals:**
- 不实现注册、密码登录、第三方鉴权
- 不保留数据库玩家档案作为该流程的前置依赖
- 不保证断线重连后认回同一个匿名玩家
- 不在本次变更中设计正式生产可用的安全身份方案

## Decisions

### 1. 由服务端分配临时玩家，而不是客户端上传 `playerID`

选择：
- 登录请求改为匿名入场请求，不再要求客户端提供权威 `playerID`
- 服务端在 `RecevicePlayerLogin` 中基于当前 session 创建临时 `Player`
- 服务端生成运行期唯一的临时 `playerID`，并通过登录响应回传给客户端

原因：
- 这和现有“后续逻辑依赖 `session.player`”的服务器结构一致
- 可以消除客户端伪造 `playerID` 的入口
- 可以保留最小必要的玩家标识，满足匹配和日志追踪

备选方案：
- 客户端继续上传随机名字作为 `playerID`
  - 放弃原因：仍然把权威身份交给客户端，和“以服务端实现为准”的目标冲突
- 完全不回传任何 `playerID`
  - 放弃原因：客户端调试、日志、后续消息归属展示都会失去稳定标识，不利于 demo 排查问题

### 2. `LoginWindow` 只负责“进入游戏”，不再承担账号含义

选择：
- 保留当前按钮入口和场景切换职责
- 弱化或去除“账号/密码”语义
- 如果输入框暂时保留，其值仅作为本地展示或临时昵称候选，不作为权威身份

原因：
- 最小化 UI 改动成本
- 避免协议和 UI 含义继续错位

备选方案：
- 完全删除输入框和随机名字
  - 放弃原因：虽然更纯粹，但会让本次变更同时包含更多 UI 调整，不是最简路径

### 3. 保留现有 `LoginService` 入口，但去掉对数据库和外部身份的依赖

选择：
- 继续通过 `PlayerLoginMsg_s -> LoginService` 进入登录链路
- `LoginService` 不再以客户端传入 `playerID` 查找或创建玩家
- 最简实现中优先走内存态临时玩家创建

原因：
- 最大化复用现有服务分层
- 避免对匹配和对局初始化路径做无关重写

备选方案：
- 彻底删除登录协议，连接建立后自动登录
  - 放弃原因：虽然也可行，但会把“连接成功”和“用户明确进入游戏”合并，改变客户端当前流程控制点

### 4. 纯 session 方案明确不覆盖重连恢复

选择：
- 在规格和实现中显式说明：session 丢失后，不保证恢复到原匿名玩家
- 现有基于 `playerID` 的重连记录逻辑不作为本次方案能力承诺

原因：
- “纯 session”与“跨 session 恢复身份”天然冲突
- 先把最小链路跑通，比保留一个语义不自洽的伪重连更重要

备选方案：
- 同时引入 reconnect token
  - 放弃原因：这已经超出“纯 session 最简易方案”的范围

## Risks / Trade-offs

- [现有重连逻辑将弱化或失效] → 在实现时显式关闭或绕过基于旧 `playerID` 的重连承诺，并在 UI/日志中说明这是 demo 限制
- [客户端仍保留账号输入框会造成理解偏差] → 将文案改为“昵称/显示名（可选）”或在窗口上改成“进入游戏”
- [登录响应结构可能需要扩展] → 在协议层增加服务端分配标识字段，同时保持调用链最小改动
- [数据库相关代码仍残留] → 本次仅解除登录前置依赖，不强求一次性删除所有数据库代码

## Migration Plan

1. 先修改协议定义，明确登录请求不再依赖客户端 `playerID`，登录响应回传服务端分配的运行期玩家标识。
2. 调整服务端 `LoginService`，改为基于当前 session 创建临时玩家并绑定 `session.player`。
3. 调整客户端 `LoginWindow` 和登录调用点，点击后发起匿名入场，不再把输入框内容作为权威身份上传。
4. 保持匹配和对局初始化继续读取服务端返回的玩家上下文。
5. 验证单客户端进入、双客户端匹配、对局帧同步基本链路。
6. 如出现兼容问题，可临时回退到“客户端上传随机 `playerID`”的旧协议，但该回退仅用于短期调试，不作为目标方案。

## Open Questions

- 登录响应里是否只返回 `playerID`，还是同时返回 `nickName` / `characterID` 以减少客户端推断
- `LoginWindow` 的账号和密码输入框是直接移除，还是先保留但重命名为 demo 文案
- 是否要在本次实现中顺手禁用或下线 `ReConnectService` 的相关入口，避免产生错误预期
